01 / SYSTEM DESIGN

One logical store.
Three independent processes.

Clients can contact any node. Followers redirect writes to the current leader. The leader serializes mutations, replicates log entries, and acknowledges only after a majority has persisted them.

02 / WRITE PATH

What happens after
PUT /kv/color?

The safety guarantee comes from order: persist locally, replicate to peers, reach quorum, then apply and acknowledge.

STEP 1 · CLIENT BOUNDARY

Only the leader accepts a mutation.

A follower returns the known leader so the client can retry. A client/request ID makes that retry idempotent instead of creating a duplicate write.

06 / PROBLEMS SOLVED

From failure mode
to engineering control.

The project is a collection of safety decisions. Each mechanism exists because a specific distributed-systems failure makes the simpler design incorrect.

PROBLEM

Single-node failure loses availability

↓SOLUTION

Replicated log, randomized elections, heartbeats, and majority-based leadership.

PROBLEM

Two leaders can claim authority

↓SOLUTION

Monotonic terms, one persisted vote per term, and step-down on higher-term messages.

PROBLEM

A retry can apply a write twice

↓SOLUTION

Persisted client/request IDs with same-command replay and conflict rejection.

PROBLEM

Quorum contact alone can allow a stale read

↓SOLUTION

A committed current-term no-op barrier before serving linearizable reads.

PROBLEM

An old leader remains alive after partition

↓SOLUTION

Quorum-confirmed reads and writes; non-persistent peer connections reflect network state.

PROBLEM

Logs grow and slow follower recovery

↓SOLUTION

Automatic snapshots, absolute log indexes, compaction, and InstallSnapshot RPC.

07 / INTERVIEW MODE

Explain the system
from first principles.

Use these prompts to walk through the design. Open any question for a concise answer, then follow the source links for implementation detail.

01Why does a three-node cluster tolerate only one failure?+

A commit needs a majority: two votes or acknowledgements. With one node unavailable, two remain and can progress. With two unavailable, the survivor cannot distinguish failure from partition and must stop committing to preserve safety.

02What happens when the current leader crashes?+

Followers stop receiving heartbeats. After randomized election timeouts, one becomes candidate, increments the term, votes for itself, and requests votes. A candidate with an up-to-date log becomes leader after receiving two votes.

03Why can’t the isolated old leader keep writing?+

It may append locally, but cannot collect a second acknowledgement. Without a majority, it cannot advance the commit index or report success. When connectivity returns, the higher-term leader overwrites any conflicting uncommitted suffix.

04How is a GET made linearizable?+

Reads are leader-only and quorum-confirmed. A newly elected leader first commits an entry from its current term, establishing authority over committed history before it serves the read.

05How does a follower recover after missing compacted entries?+

If the follower's next required index precedes the leader's retained log, the leader sends a snapshot. The follower installs it atomically, restores key/value and deduplication state, then receives the remaining log suffix normally.

06What real bug did fault testing uncover?+

Leaders were still processing their election timers, causing unnecessary term churn during sustained writes. The fix made leaders ignore election timeouts, and a race-enabled regression test now protects that state-machine rule.
